## Implementation Details

### Migration Logic

#### Phase 1: Guardian User Conversion

```typescript
// For each guardian user:
1. Create provider entity (category: "guardian")
2. Update students: guardianId → providerId
3. Update classes: isGuardianLinked → providerId set
4. Maintain guardianId/isGuardianLinked for rollback safety
```

#### Phase 2: Orphan Student Handling (NEW)

```typescript
// For students without schoolId/providerId/guardianId:
1. Detect orphan students
2. Create single pseudo-provider:
   - Name: {Teacher'sPVTclass} / {ชั้นเรียนส่วนตัวของครู}
   - Category: "personal"
   - isAutoGenerated: true
3. Link all orphan students to pseudo-provider
```

#### Phase 3: Verification & Cleanup

```typescript
// After migration verified working:
1. Run verifyCleanup query → check status
2. Run cleanupDeprecatedFields mutation:
   - Phase "students": Remove guardianId
   - Phase "classes": Remove isGuardianLinked
   - Phase "all": Remove both
3. Safety: Only removes if providerId exists
```

### Safety Measures

1. **Dry-Run Mode**: Preview all changes without modifying data
2. **Rollback Capability**: Complete reversal including pseudo-provider deletion
3. **Phased Cleanup**: Gradual removal of deprecated fields
4. **Verification Query**: Real-time status checking
5. **Pre-flight Checks**: Connection and backup validation
6. **Interactive Confirmations**: Prevents accidental execution
