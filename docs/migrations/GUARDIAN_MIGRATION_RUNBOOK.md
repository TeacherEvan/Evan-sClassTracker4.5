## Overview

### What This Migration Does

1. **Converts Guardian Users → Provider Entities**
   - Each guardian user gets a corresponding provider entity
   - Category: "guardian"
   - Maintains all relationships

2. **Creates Pseudo-Provider for Orphan Students**
   - Students without schoolId/providerId/guardianId
   - Provider name: `{Teacher'sPVTclass}` / `{ชั้นเรียนส่วนตัวของครู}`
   - Category: "personal"
   - `isAutoGenerated: true`

3. **Updates Data References**
   - Students: `guardianId` → `providerId`
   - Classes: `isGuardianLinked=true` → `providerId` set

4. **Cleanup (Optional, Post-Migration)**
   - Removes deprecated `guardianId` from students
   - Removes deprecated `isGuardianLinked` from classes
   - Keeps guardian role in schema for data safety

### Why This Migration

- **Simplifies Architecture**: One system (providers) instead of two (guardians + providers)
- **Improves Maintainability**: Fewer conditional paths in code
- **Better UX**: Consistent provider selection across all workflows
- **More Flexible**: Easy to add new provider types

## Migration Steps

### Step 1: Dry Run (Recommended)

Run the migration in preview mode to see what would happen:

```powershell
# From project root
.\scripts\run-guardian-migration.ps1 -DryRun $true
```

**What It Does**:

- Shows all operations without making changes
- Validates admin ID
- Checks data consistency
- Provides detailed log

**Interactive Prompts**:

1. Enter Admin ID (from Convex users table)
2. Confirm preview review
3. Script provides Convex Dashboard function call instructions

**In Convex Dashboard**:

1. Go to **Functions** → `guardianToProviderMigration:migrateGuardiansToProviders`
2. Enter parameters:

   ```json
   {
     "adminId": "jd7...",  // Your admin ID
     "dryRun": true
   }
   ```

3. Click **Run Function**
4. Review output logs

**Review Checklist**:

- [ ] All guardian users listed
- [ ] Student counts match preview
- [ ] Orphan students identified correctly
- [ ] No errors in dry run
- [ ] Provider names look correct

### Step 2: Live Migration

If dry run looks good, run the actual migration:

```powershell
.\scripts\run-guardian-migration.ps1 -DryRun $false -Backup $true
```

**What It Does**:

1. Creates backup (if not already done)
2. Prompts for confirmation
3. Provides Convex Dashboard instructions

**In Convex Dashboard**:

1. Go to **Functions** → `guardianToProviderMigration:migrateGuardiansToProviders`
2. Enter parameters:

   ```json
   {
     "adminId": "jd7...",
     "dryRun": false
   }
   ```

3. Click **Run Function**
4. **WAIT** for completion (may take 1-5 minutes depending on data size)

**Expected Success Output**:

```json
{
  "success": true,
  "dryRun": false,
  "guardiansProcessed": 3,
  "orphanStudentsProcessed": 8,
  "pseudoProviderCreated": true,
  "successfulMigrations": 4,
  "failedMigrations": 0,
  "migrationLog": [
    {
      "guardianId": "...",
      "guardianUsername": "guardian1",
      "providerId": "...",
      "studentsUpdated": 10,
      "classesUpdated": 18,
      "status": "success"
    },
    {
      "type": "orphan_students",
      "pseudoProviderId": "...",
      "studentsUpdated": 8,
      "classesUpdated": 0,
      "status": "success"
    }
  ]
}
```

**Warning Signs**:

- `success: false` - Migration had errors
- `failedMigrations > 0` - Some items failed
- Check `errors` array for details

## Cleanup

**⚠️ ONLY RUN AFTER MIGRATION IS VERIFIED WORKING!**

Cleanup removes deprecated fields permanently. Ensure:

- Migration completed successfully
- System tested and working
- Backup is safe and recent
- **AT LEAST 48 HOURS** have passed since migration

### Cleanup Phases

You can run cleanup in phases for extra safety:

#### Option 1: Clean Students Only

```powershell
.\scripts\run-guardian-migration.ps1 -Cleanup $true -CleanupPhase "students"
```

**In Convex Dashboard**:

```json
{
  "adminId": "jd7...",
  "confirm": true,
  "phase": "students"
}
```

Removes `guardianId` from students that have `providerId` set.

#### Option 2: Clean Classes Only

```powershell
.\scripts\run-guardian-migration.ps1 -Cleanup $true -CleanupPhase "classes"
```

**In Convex Dashboard**:

```json
{
  "adminId": "jd7...",
  "confirm": true,
  "phase": "classes"
}
```

Removes `isGuardianLinked` from classes that have `providerId` set.

#### Option 3: Clean All (Recommended)

```powershell
.\scripts\run-guardian-migration.ps1 -Cleanup $true -CleanupPhase "all"
```

**In Convex Dashboard**:

```json
{
  "adminId": "jd7...",
  "confirm": true,
```

## Rollback Procedure

> **⚠️ WARNING**: Use ONLY if migration fails or needs to be undone

### When to Rollback

- Migration failed with errors
- Data corruption detected
- Critical bugs discovered after migration
- User workflows broken

### Rollback Steps

1. **Stop all users from accessing the system** (if possible)

2. **Run rollback mutation**:

**In Convex Dashboard**:

1. Go to **Functions** → `guardianToProviderMigration:rollbackMigration`
2. Enter parameters:

   ```json
   {
     "adminId": "jd7...",
     "confirm": true
   }
   ```

3. Click **Run Function**

**What Rollback Does**:

- Clears `providerId` from students that have `guardianId`
- Clears `providerId` from classes that have `isGuardianLinked`
- Deletes auto-generated pseudo-provider
- **Does NOT delete manually created guardian providers**

1. **Verify Rollback**:
   - Check students have `guardianId` but no `providerId`
   - Check classes have `isGuardianLinked` but no `providerId`
   - Test guardian workflows still work

2. **Restore from Backup (if needed)**:

   ```powershell
   # If rollback doesn't fully restore state
   .\scripts\restore-from-mongodb.ps1
   # Select pre-migration backup
   ```

## Troubleshooting

### Issue: "Unauthorized: Only admins can run migrations"

**Cause**: Invalid or non-admin user ID provided

**Solution**:

1. Open Convex Dashboard → **Data** → `users` table
2. Find your admin user
3. Copy the `_id` field (starts with table prefix, e.g., `jd7...`)
4. Verify `role` field is `"admin"`

### Issue: Migration times out or hangs

**Cause**: Large dataset, slow network, or database lock

**Solution**:

1. Check Convex Dashboard logs for errors
2. Wait longer (migrations can take 5-10 minutes for large datasets)
3. If truly stuck, run rollback and try again
4. Consider running in smaller batches (contact support for batch migration script)

### Issue: "Provider not found" errors

**Cause**: Provider creation failed but migration continued

**Solution**:

1. Check migration log for which guardian failed
2. Manually create provider for that guardian:

   ```json
   {
     "name": "Guardian - username",
     "nameTh": "ผู้ปกครอง - username",
     "category": "guardian",
     "createdBy": "<admin-id>"
   }
   ```

3. Re-run migration (it will skip already-migrated guardians)

### Issue: Orphan students not getting pseudo-provider

**Cause**: Students have `schoolId` or `providerId` but you didn't realize

**Solution**:

1. Run preview again to check actual orphan count
2. Manually inspect students in Convex Dashboard
3. Verify they truly have no links: `!schoolId && !providerId && !guardianId`

### Issue: Cleanup removes data it shouldn't

**Cause**: Running cleanup before migration is verified

**Solution**:

1. **NEVER run cleanup immediately after migration**
2. Wait at least 48 hours
3. Test thoroughly before cleanup
4. Cleanup only removes deprecated fields from records that have the new field set

### Issue: Application breaks after migration

**Symptoms**: Errors in UI, failed queries, missing data

**Solution**:

1. Check browser console for errors
2. Check Convex logs for failed mutations
3. Run verification query to check data integrity
4. If critical, run rollback immediately
5. If minor bugs, file issues and fix incrementally
